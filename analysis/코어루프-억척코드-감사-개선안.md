# 코어 에이전트 루프 — "억척스러운 구현" 감사 및 표준 개선안

- 대상: `api/app/` 코어 9파일 (loop.py, llm_step.py, llm.py, main.py, config.py, models.py, prompts.py, utils.py, mcp_server.py)
- 경계 준수: `retrieval/`, `tools/`, `ui/`, `pipeline/`, `api/data/`는 분석하지 않음 (다른 리서처 담당). 다만 loop/llm_step에서 tools/ 파일을 *호출하는 지점*의 인터페이스는 코어 파일 안에 있으므로 그 한도에서만 인용함.
- 전체 신뢰도: **높음** — 모든 코드 인용은 2026-09-29 현재 워크스페이스 파일에서 직접 확인. 외부 라이브러리 주장(litellm Router, MCP SDK)은 공식 문서/README 대조 완료.

---

## 결론 요약

이 코드베이스의 억척스러움은 크게 4가지로 수렴한다:

1. **모델 출력에 대한 후처리 방어벽** (loop.py "위생 규칙" + llm_step.py 텍스트 툴콜 파싱) — 약한 무료 모델의 증상을 프롬프트 + 정규식 이중으로 막고 있으며, 프롬프트(prompts.py `JODAL_STATS_GUIDANCE`)와 코드가 **같은 규칙을 이중으로 유지**한다.
2. **표준 라이브러리가 이미 있는 것의 수동 재구현** — 재시도/폴백(`tenacity`가 의존성에 있는데 import 0회, litellm이 폴백 내장), 예외 분류(문자열 매칭), 스트리밍 청크 정규화, JSON 스캔.
3. **프로토콜 위반** — `text/event-stream`을 선언하고 NDJSON을 내보내는 SSE 엔드포인트.
4. **도메인 상수의 코어 침투** — 특정 툴 이름, 한국어 어미 목록, 특정 정부 도메인이 범용 루프 코어에 하드코딩.

가장 효과 큰 단일 개선은 **"마지막 사이클 reminder" 방식을 "툴 수집 → 답변 전용 호출" 2-페이즈로 바꾸는 것**과 **폴백/재시도를 litellm.Router로 교체**다. 이 둘만으로 위생 규칙의 상당수가 필요 없어진다.

## A. loop.py (719줄) — 위생 15종 + 수동 재시도

### A1. 한국어 "예고 문장" 탐지 정규식 (PROMISE_RE)
- **위치**: loop.py:53-67 (`_PROMISE_VERB`, `_PROMISE_END`, `PROMISE_RE`), 사용처 L105-183
- **현재 구현**:
  ```python
  _PROMISE_VERB = r"(?:조회|검색|확인|정리|살펴|탐색|안내|찾|모아|나열|작성|제시|전달|드릴|보여|알려|답변|체가)"
  _PROMISE_END = r"(?:하겠습니다|하겠|할게요|할까|하러|해두겠|거든요|보겠습니다|...어보려고)"
  PROMISE_RE = re.compile(_PROMISE_VERB + r"[^.!?\n]{0,10}?" + _PROMISE_END)
  ```
- **왜 억척스러운가**: 한국어 활용 어미를 손으로 열거한 규칙집이다. 주석 스스로 "실측에서 동사가 제각각이라 열거가 실제 문장을 놓쳤다"(L56-57)고 시인한다. 즉 **열거형 접근이 실패했음을 데이터로 확인하고도 같은 방식을 확장**한 것. 새 어미("해볼게요"→"어볼게요"를 뒤늦게 추가, L64)가 나올 때마다 패치해야 하는 구조다. 또 `_is_promise_only`(L139)는 "마지막 문장이 예고면 재촉"인데, 이 재촉 자체가 `TOOL_REQUIRED_REMINDER`(L71)로 **특정 툴 이름 `mcp_jodal_search_reports`를 루프 코어에 박아넣는다**.
- **개선안**:
  1. **근본 해법(권장): 2-페이즈 루프.** 툴 결과 수집이 끝나면 tool 없이 "수집된 결과로 최종 답변을 작성하라"는 **별도의 답변 전용 LLM 호출**을 만든다. 이 호출에는 툴이 없으므로 예고 문장이 나올 이유 자체가 사라지고, `PROMISE_RE`/`_is_promise_only`/`_is_all_narration`/`TOOL_REQUIRED_REMINDER`/`PROMISE_MAX_NUDGES`(총 ~120줄)가 전부 흡수된다. 이 구조(Act → Answer 분리)는 최신 에이전트 프레임워크(OpenAI Agents SDK, LangGraph `create_react_agent`의 response-format 단계)가 채택한 표준 패턴이다.
  2. 완화책(2-페이즈로 못 옮길 때): nudge 판정을 정규식이 아니라 **툴 호출 여부라는 구조적 신호로만** 한다 — `finish_reason == "stop"`이고 `tool_calls`가 없고 `saw_tool_payload`가 True면 무조건 답으로 인정. 어미 정규식은 한국어 특화 지식이라 범용 루프에 둘 자리가 아니다.
- **영향도**: **High** — 유지 비용 최대, 한국어·도메인 지식이 코어에 침투한 대표 사례.

### A3. 위조 링크 제거 (strip_fabricated_links) + 유령 링크 줄 정리
- **위치**: loop.py:275-330 (`_URL_RE`, `_MD_LINK_RE`, `_DANGLING_LINK_LINE_RE`, `strip_fabricated_links`)
- **현재 구현**: 툴 응답에 실제로 등장한 URL 집합을 만들어(allowed), 마크다운 링크의 href가 거기 없으면 지운다. 지운 뒤 "- 바로 열기" 같은 한국어 링크 잔해 줄도 정규식으로 지운다: `(?:바로 ?열기|바로 ?보기|여기|링크|자세히 ?보기|접속|이동|열기|보기|링크보기)`.
- **왜 억척스러운가**: (1) "모델이 URL을 지어낸다"는 증상 자체는 근본 원인(기억으로 답변)의 2차 증상. (2) 한국어 UI 문구 열거는 새 표현마다 놓친다. (3) `_URL_TRAIL = ".,);]\\"` 같은 후행문자 수동 컷, 주석에 "역슬래시를 반드시 제외한다… JSON 이스케이프된 `\"` 때문에 오판된다"(L305-307) — 즉 **툴 페이로드를 문자열 regex로 긁으면서 생기는 인코딩 경계 문제를 regex 세부조정으로 해결** 중.
- **개선안**: URL 허용집합 아이디어 자체(grounded links)는 SOTA 정합성 기법이 맞다. 그러나 구현은: (1) 툴 응답 파싱을 **JSON으로 구조화된 `SearchDoc.link`에서** 가져오기 — 이미 `ToolResponse.rich_response`의 `search_docs`에 구조화된 링크가 존재한다(models.py SearchDoc). (2) 유령 줄 정리는 정규식 목록 대신 "링크가 삭제된 결과 마크다운 라인이 링크만 남았는지" 판정 일반화.
- **영향도**: Medium — 기능은 유효하나 구현이 문자열 경계에서 취약.

### A4. report_id 5자리 숫자 판별/제거 (strip_unknown_report_ids, hide_report_ids)
- **위치**: loop.py:332-414 (`_REPORT_ID_RE`, `_looks_like_report_id`, `_sub_outside_urls`, `strip_unknown_report_ids`, `hide_report_ids`)
- **현재 구현**: `(?<![\d])(\d{5})(?![\d])`로 5자리 숫자를 찾고, "00"으로 시작하면(L337-340, 실제 범위 00001~00999) report_id로 간주해 지운다. URL 내부(`?g2bOpen=00262`)는 보호하려고 `_URL_SPAN_RE`으로 URL 구간을 먼저 찾아 제외한다(L347-362).
- **왜 억척스러운가**: 데이터의 id 포맷("앞자리 0인 5자리")이 코어 정규식에 박혀 있다. "5자리 개수, 10자리 품목분류코드, 연도는 건드리지 않는다"는 예외도 주석로 나열(L372-374). URL 보호를 위해 정규식 위에 또 정규식을 얹은 이중 구조. 주석이 시나리오 3개(실측 사례)를 들어 설명해야 하는 복잡도.
- **개선안**: **출력 스키마로 해결** — 최종 답변 생성 시(2-페이즈의 답변 전용 호출) LLM에게 "보고서명+링크만 쓰고 ID는 쓰지 마라"가 아니라, **답변 후처리에서 id가 아니라 `search_docs`의 grounded 매칭으로만 ID를 유지**하는 규칙은 이미 `known_ids` 로직이 있다. 더 근본적으로는 A1의 2-페이즈 + 구조화된 인용(`[N]` 인덱스 → SearchDoc 매핑, 이미 존재: `result.citation_docs`)으로 답변이 링크를 조립하게 하면 "모델이 ID를 지어내는" 경로가 사라진다. id 포맷 상수는 tools/ 계층(데이터 소유자)으로 이동.
- **영향도**: Medium — 정확히 동작하지만 도메인 포맷 지식이 코어에 있음.

### A6. 수동 레이트리밋 재시도 (문자열 매칭 + sleep(5))
- **위치**: loop.py:260-273 (`_is_rate_limit`), L472-489 (재시도 블록)
- **현재 구현**:
  ```python
  def _is_rate_limit(error):
      name = type(error).__name__.lower(); msg = str(error).lower()
      return "ratelimit" in name or "rate_limit" in msg or "rate limit" in msg or "429" in msg or "tpm" in msg
  # ...
  if _is_rate_limit(e) and cycle == 0:
      time.sleep(5)   # Tiny TPM tiers need a beat...
      step_result, step_packets = run_llm_step(...)  # 1회만 재시도
  ```
- **왜 억척스러운가**: (1) 예외 타입 판별을 문자열 포함 검사로 — litellm은 `litellm.RateLimitError` 등 **표준 예외 계층**을 제공하며 `isinstance`로 판별 가능하다. (2) `sleep(5)` 하드코딩, 백오프 없음, 재시도 1회만, 사이클 0에서만. (3) **`tenacity==9.1.2`가 pyproject.toml dependencies에 있는데 app/ 코드에서 import가 0회다** (전체 grep 확인). 폴백 체인(llm.py)과 이 재시도가 서로 다른 계층에서 각자 ad-hoc으로 존재.
- **개선안**: 재시도/폴백을 **litellm.Router**로 일원화 — 공식 문서(docs.litellm.ai/docs/routing) 확인: "cooldowns, fallbacks, timeouts and retries (fixed + exponential backoff) across multiple deployments/providers"를 내장. xkiro/agnes는 OpenAI 호환이므로 litellm `openai/` + `api_base` 라우팅으로 등록 가능(아래 B4 참조). 루프 안의 재시도 블록은 삭제하고, `Retry-After` 존중·지수 백오프는 Router 설정(`num_retries`, `retry_after`). 코드 기준으로는 tenacity `@retry(retry=retry_if_exception_type(RateLimitError), wait=wait_exponential_jitter)` 한 줄로도 대체 가능하나 Router가 폴백까지 흡수하므로 Router 권장.
- **영향도**: **High** — 이미 의존성에 있는 도구를 안 쓰고 있고, 문자열 매칭은 프로바이더 바뀌면 조용히 실패한다.

### A7. 툴별 특수 규칙이 루프에 하드코딩
- **위치**: loop.py:551-560 (resolve_items 2회 제한 — `if r.tool_name == "mcp_jodal_resolve_items"`), L561-574 (web_search 후 open_url nudge), L71-75 (TOOL_REQUIRED_REMINDER에 툴 이름)
- **현재 구현**: 특정 툴 이름 3개(`mcp_jodal_resolve_items`, `web_search`, `mcp_jodal_search_reports`)가 루프 코어의 분기 조건으로 등장. resolve_items는 "누적 2회 이후 스킵 통보"라는 도메인 정책이 한국어 리마인더 문장로 박혀 있다.
- **왜 억척스러운가**: 범용 에이전트 루프가 특정 MCP 툴의 사용 정책을 알고 있다. 툴 이름이 바뀌면(서버 이름 `jodal` → 다른 것) 조용히 무효가 된다. `has_jodal_tools` 판정(L463-466)도 `"jodal" in t.name` 문자열 포함 검사.

- **영향도**: **High** — 코어/도메인 결합의 핵심 원천.

### A8. 스트림 패킷 후처리 시 조인→청소→재분할
- **위치**: loop.py:185-239 (`_clean_pseudo_tool_call_packets`)
- **현재 구현**: 이미 스트리밍된 `message_delta` 패킷들을 모아(join) 문자열 청소를 하고, 첫 패킷 하나에 통짜로 다시 넣는다.
- **왜 억척스러운가**: 스트리밍 아키텍처와 후처리 아키텍처가 충돌하는 지점. 사용자는 "스트리밍"을 보고 있지만 실제로는 청소 여부에 따라 재조립된 덩어리가 늦게 도착할 수 있다. 근본적으로 **답변 위생은 스트리밍 채널이 아니라 최종 답변 계약에서 해결할 문제**.
- **개선안**: 2-페이즈 개선(A1)과 함께 — 도구 사용 페이즈는 스트리밍 그대로 두고(과정 표시), **최종 답변 페이즈는 청소 후 단일 전송**으로 계약을 명확히 한다. 그러면 "조인→청소→재분할" 기계가 필요 없다.
- **영향도**: Medium.

## B. llm_step.py (505줄) — 텍스트 툴콜 파싱 + JSON 스캔

### B1. balanced-brace JSON 스캔 (_find_json_objects)
- **위치**: llm_step.py:156-178
- **현재 구현**:
  ```python
  def _find_json_objects(text: str) -> list[dict]:
      # 중첩 depth를 세며 { ... } 후보를 찾아 json.loads 시도 (Onyx 포트)
  ```
- **왜 억척스러운가**: (1) **문자열 리터럴 안의 `{`/`}`를 세지 않는다** — `{"query": "가격 {3000원}"}` 같은 값이 있으면 depth가 틀어져 유효한 JSON 객체를 못 찾거나 잘못된 스팬을 `json.loads`로 시도한다. 주석의 근거가 "Onyx 포트"인데 Onyx도 같은 결함을 가진 것으로 보이며, JSON 스펙을 무시한 스캔이다. (2) O(n²) (최악 경우 모든 `{`에서 끝까지 순회). (3) 어떤 JSON이 "툴콜인지" 판별하는 `_match_json_to_tool`(L340-373)은 4단계 추측(name 필드 → function.name → 툴명 키 → required-props 부분집합)으로 이어지는데, 이는 **임의의 JSON을 억지로 툴콜로 해석**하려는 시도라 오탐(툴 파라미터와 우연히 겹치는 필드를 가진 일반 텍스트 JSON을 툴콜로 실행) 위험이 있다.
- **개선안**: **이 폴백 전체를 제거하는 것이 표준 개선안이다.** 근거: (1) 텍스트 채널로 툴콜을 흘리는 건 tool-call 파싱 계층(LiteLLM/프로바이더)의 정규화 문제이거나 모델이 약한 것 — LiteLLM이 `stream`에서 표준 `tool_calls` delta로 정규화해주는 것이 계약이며, delta 조립(`_update_tool_call_with_delta`, L72-89)은 이미 올바르게 구현돼 있다. (2) JSON이 중간에 잘려 도착하는 스트리밍 문제라면 `partial-json`류 라이브러리가 표준 해법이지만, 그것은 이미 LiteLLM 내부(`stream_chunk_builder`)에 있다. 텍스트-채널 JSON 스캔은 Onyx의 레거시 관용구이지 SOTA가 아니다. (3) 툴을 존중하지 않는 모델에 대한 표준 해법은 `tool_choice="required"`(지원 시) 또는 모델 교체이지, 텍스트에서 툴콜을 점치는 게 아니다.
- **영향도**: **High** — 결함 있는 파서가 오탐을 만들 수 있는 위험 + 유지 비용.

### B2. 비표준 텍스트 툴콜 문법 4종 정규식 (_TEXTUAL_TOOL_CALL_RE)
- **위치**: llm_step.py:194-204, 파싱 L206-269, 폴백 사용처 loop.py:507-530
- **현재 구현**:
  ```python
  _TEXTUAL_TOOL_CALL_RE = re.compile(r"""
    \[\s*tool\s*:\s*(?P<a_name>...)\s*(?P<a_args>[^\]\n]*)\]
    | \[\s*(?P<b_name>...)\(\s*(?P<b_args>...)\s*\)\s*\]
    | <tool\s+name\s*=\s*["'](?P<c_name>...)["']\s*>(?P<c_args>.*?)</tool>
    | <tool\s*>\s*(?P<d_name>...)(?P<d_args>[^<]*)</tool\s*> """, ...)
  ```
  "Non-JSON tool-call syntaxes we have actually seen" — 관찰된 4가지 비표준 문법. `_parse_textual_args`는 `key: value, key: value` 형태까지 수동 파싱.
- **왜 억척스러운가**: 모델별 버그 문법을 정규식 목록으로 추적하는 것 — 새 모델이 새 문법을 흘리면 또 추가해야 한다. B1과 같은 근본 원인(약한 모델 + 파싱 계층 부실)의 증상 대응. 단, 사용자 텍스트 오염 방지(`name not in name_to_params`면 원문 유지, L253-255) 같은 방어는 잘 돼 있다.
- **개선안**: B1과 동일하게 제거 방향. 예외적으로 유지하려면 폴백은 "프로바이더/모델 감지 → 그 모델에서만 활성화"하는 게 최소한의 범위 제한. OpenAI 표준 tool-call 채널을 못 쓰는 모델이라면 모델을 바꾸는 것이 답(무료 티어 체인 llm.py 참조).
- **영향도**: High (B1과 묶음).

### C1. DIRECT_PROVIDERS 프로바이더별 if 분기 + 수동 폴백 for 루프

(2) xkiro/agnes를 "직결"로 별도 코드 경로를 둔 이유가 주석에 명시돼 있지 않고, OpenAI 호환이면 litellm에서도 `openai/<model>` + `api_base`로 동일 호출이 가능하다. `_Endpoint.litellm_model`(L38-50)은 "groq/openai/gpt-oss-120b" 같은 이중 프리픽스 규칙을 설명하는 주석을 갖고 있을 만큼 이미 프리픽스 처리가 미묘하다.       {"model_name": "primary", "litellm_params": {"model": "groq/openai/gpt-oss-120b", "api_key": ...}},


- **영향도**: **High** — 코드 대폭 감소 + 신뢰성 기능(미드스트림 폴백, cooldown) 공짜로 확보.

- **왜 억척스러운가**: (1) 자기 자신에 대한 네트워크 라운드트립은 직접 호출 대비 지연·직렬화 비용·장애 포인트(포트 불일치)를 추가한다. 포트 불일치 사고가 실제로 발생했고 이를 막으려고 mcp_server.py에 `_verify_self_mcp`(asyncio.sleep(1.0) 후 자기 discover, E3 참조)라는 **또 다른 억척 코드**가 필요해졌다 — 문제가 문제를 낳는 구조. (2) 배포 스크립트의 shell quoting 버그를 애플리케이션 에러 메시지로 가이드하는 건 계층 침범.
- **개선안** (사용자가 명시한 "MCP 클라이언트가 자기 /mcp를 HTTP로 호출하는 구조"): MCP Python SDK v1(현재 mcp==1.28.1)은 `mcp.shared.memory.create_connected_server_and_client_session` — **프로세스 내 in-memory 트랜스포트로 실제 ClientSession**을 제공한다(외부 검색으로 다수 소스 확인; v2에서는 `Client`가 커스텀 트랜스포트 지원, 공식 README 확인). 즉 "MCP 프로토콜 계층 유지"라는 그들의 설계 목표(독립 검증 가능성)를 유지하면서 HTTP 라운드트립과 포트 민감성을 제거할 수 있다. 단, in-memory로 바꾸면 "curl로 독립 검증"은 `/mcp` HTTP 엔드포인트를 계속 마운트해 두면 별개로 유지된다 — **검증 경로(HTTP)와 런타임 경로(in-memory)를 분리**하는 것이 최선. 배포 민감성(PORT)도 사라짐. 요약: 동일 서버 인스턴스를 두 경로로 노출.
- **영향도**: **High** — 사용자가 지목한 구조 자체. 표준 프로토콜 메커니즘(SDK in-memory 세션)으로 대체 가능.

### E3. warmup의 프라이빗 접근 + _verify_self_mcp의 sleep(1.0)
- **위치**: mcp_server.py:285-303 (`search_hybrid._lazy` — noqa: SLF001로 프라이빗 직접 호출), L305-333 (`_verify_self_mcp`: `await asyncio.sleep(1.0)`로 uvicorn 바인딩 대기 후 자기 discover)
- **왜 억척스러운가**: (1) `search_hybrid._lazy`는 다른 모듈의 프라이빗 함수를 우회 호출(초기화 API가 없어서). (2) `sleep(1.0)`은 레이스 컨디션을 시간으로 회피하는 전형적 anti-pattern — 느린 기기에서는 실패, 빠른 기기에서는 1초 낭비. E2의 포트 문제가 원인이라 E2 해결 시 필요 없어진다.
- **개선안**: E2 적용 시 `_verify_self_mcp` 삭제(또는 HTTP 외부 엔드포인트 health-check로 축소). `_lazy`는 retrieval/ 계층에 공개 초기화 함수를 요청하는 인터페이스 수정(다른 리서처 영역과의 협업 포인트로 기록).
- **영향도**: Medium (E2에 종속).

## G. models.py / utils.py / mcp_server.py 잔여

- **models.py**: 깨끗함. Pydantic 모델 정의만. 감사 대상 없음.
- **utils.py**: `sanitize_string`(NUL/서로게이트 제거)은 Onyx 포트, 표준적. 감사 대상 없음.
- **mcp_server.py `_SPECS` 수동 스키마 정의 (L50-212)**: 11개 툴의 inputSchema를 손으로 JSON Schema로 작성. MCP Python SDK는 docstring+타입힌트에서 스키마를 자동 생성하는 `FastMCP`(`@mcp.tool()`)를 제공(공식 README 확인: "no JSON Schema — two type-hinted Python functions"). 다만 기존 `fn` 시그니처 재사용과 "mcp/ Worker와 동일한 이름·스키마" 호환 목표(파일 헤더 주석)가 있어 완전 자동화는 트레이드오프. **개선안**: FastMCP의 `@mcp.tool()`로 전환하되 스키마 호환은 통합 테스트로 고정. **영향도**: Low-Medium (중복 제거지만 동작은 이미 올바름).
- **mcp_server.py L44-45**: `INPUT_ERROR = -32602` / `INTERNAL_ERROR = -32000` 상수가 **정의만 되고 사용처 없음**(raise ValueError/RuntimeError → MCP 라이브러리가 알아서 매핑). 데드 코드 — 삭제. **영향도**: Low.
