# LLM-heavy vs Deterministic-first: 장단점과 파워풀한 쪽

> 비교 대상
> - **A (LLM-heavy)**: LLM 생성 → 임베딩 → LLM Rerank → LLM 구조화 답변
> - **B (Deterministic-first, 현행)**: 템플릿 렌더 → 임베딩 → Stage solver → 코드 조립 답변
> - **C (Single-call)**: 보고서 131건 명세(검색조건/출력열/desc/name)를 프롬프트에 통째로 넣고 단일 LLM 호출로 구조화 매칭

## 1. 측정된 팩트 (우리 시스템 실측)

| 항목 | A (측정분) | B (측정분) |
|---|---|---|
| recall@5 | 미측정 (Rerank 도입 전 수치 없음) | **0.925** |
| family 혼동 (신호) | 미측정 | **0.0** |
| dims_miss | 미측정 | **0.0** |
| 지연 p95 | 4~20초 (429 시 4분 실측) | **0.5초** |
| LLM calls/query | 1+repair (프롬프트 6,800자) | **0** |
| Rerank 품질 | 동점군 오픽 실측 (00011>00010), garbage reason 검증 통과 | 해당 없음 (기계 순위) |

## 2. 장단점

### A. LLM-heavy

**장점**
- **미지의 언어에 강함**: paraphrase·신조어·오타·"MAS" 같은 미등록 표현. 규칙은 사후 대응뿐이라 항상 한 박자 느림.
- **판단 유연**: 모호 케이스에서 사람 같은 절충 가능 (이론상).
- **개발 속도 (초기)**: 규칙 설계 없이 프롬프트로 시작 가능.

**단점 (실측 기반)**
- **정확도 역전 실측**: 작은 후보군(≤3)에서 텍스트 유사도(RRF)를 이기지 못함. 검증이 형식(길이·enum)만 보니 내용 garbage가 통과.
- **비용·quota**: 쿼리당 7K자 프롬프트 + reasoning → TPM 8K턱걸이, 429 연쇄. 무료枠에서 처리량 1/3~1/10.
- **지연**: 4~20초, worst 4분. 채팅 UX 사망선.
- **비결정성**: 같은 질문 다른 답. W7 평가·디버깅·회귀 추적 곤란. 모델 교체(gpt-oss→qwen) 때마다 거동 변경 실측.
- **설명가능성 허상**: reason은 유창하나 근거 검증 없음. "그럴듯한 오답"이 제일 위험한 형태.

### B. Deterministic-first

**장점 (실측)**
- 위 표 전부. 특히 **재현성**: 같은 입력→같은 출력이라 측정·회귀·디버깅 가능 (stage 로그가 곧 근거).
- **비용 0·지연 0.5초**. quota 논쟁 자체가 없음.
- **근거 강제 가능**: 기계 생성 reason은 환각 불가. "왜 이 보고서냐"가 항상 추적됨.

**단점**
- **미등록 언어에 먹통**: MAS·신조어는 개념 등록 전까지 miss. 사후 대응 구조라 지각.
- **규칙 accretion**: 실패 1건 → 예외 1개 (S0~S5 + 면제조항들…). 복잡도 무한 증가, 상호작용 예측 곤란.
- **경계 케이스 취급 곤란**: "약간 애매한데 답은 있는" 케이스를 코드로 다 나누기 힘듦.
- **정확도 천장**: top1 0.766에서 정체. 남은 건 합성셋 한계 + 가문 내 변별 신호 부족.

## 3. C안 (Single-call) 분석

방식: 131건 명세(보고서명 + desc 요약 + 입력조건명 + 출력컬럼명)를 프롬프트에
concat → "이 중 조건을 만족하는 보고서 있으면 구조화 JSON으로" 1 call.

```text
[131 reports compact …]
사용자 질문: {q}
→ [{"report_id","match","reason","missing_capabilities","confidence"}]
```

### 토큰 실측 (우리 카탈로그 기준)

- 압축 명세: 보고서당 평균 363자, 전체 **47,675자** (max 1,941자).
- 입력換算: 한글 비중 높아 **약 2.4~4.8만 토큰/쿼리** (출력 제외).
- 현행 Rerank 프롬프트(6,800자, Top10만)의 **7배**.

### 장점

- **구현 최단**: 검색 인프라(BM25·임베딩·Stage) 전부 불필요. 오늘 저녁에 돌릴 수 있음.
- **커버리지 상한**: 후보 누락 구조적으로 없음 (전체를 봄). recall 상한 이론상 100%.
- **판단 유연**: A의 장점(미지의 언어) 전부 포함.

### 단점 (치명적 3개)

1. **quota 즉시 사망**: 무료枠 TPM 8K인데 1쿼리가 2.4만 토큰+. 분당 1쿼리도 안 나감.
   TPD 200K 기준 하루 수 쿼리. Rerank v1(7K자)보다 7배 비쌈.
2. **long-context needle 문제**: 131개 중 1개를 5만 토큰 속에서 고르기.
   앞뒤 recency bias로 중간 보고서가 묻힘 — "전체를 본다"가 "전체를 제대로 본다"가 아님.
   미측정이지만, 동점군 3개에서도 오픽 나던 모델이 131개에서 잘 고를 근거 없음.
3. **지연**: 5만 토큰 입력 추론은 reasoning high와 곱해져 수십초~수분.
   429 backoff까지 겹치면 현행 worst(4분)보다 나쁨.

### 완화책과 한계

- **prompt caching**: Groq가 캐시 히트 할인 지원. 정적 카탈로그 prefix가 캐시되면
  쿼리당 실비용은 질문+출력뿐. 단, (a) 캐시 적중률·지원 여부 실측 필요,
  (b) 유료 전환 전제, (c) needle 문제는 그대로.
- **131→축소**: family 44개 요약만 넣고 2단계로 (family 고르기 → 해당 family 상세 2차 호출).
  = 결국 검색+판정 2단 구조로 회귀. C의 단순성 상실.

### 판정

- **프로토타입용으로는 최고, 운영용으로는 불가.** 무료枠에선 선택지 아님.
- niche 1개: 보고서 수십 건 이하 소규모 or 유료+캐싱 전제면 재검토.
  우리(131건·무료枠) 조건에서는 B 조합이 그대로 우위.

## 4. 뭐가 가장 파워풀한가

**파워 = 정확도 × 신뢰도 ÷ 비용** 으로 정의하면 답은 셋 중 하나가 아니라 조합:

```text
B를 기본값으로 (빠름·쌈·재현가능·근거확정)
  +
A를 조건부로 (B가 손들 때만: 슬롯 0개 + 텍스트 유사도 약함)
  +
게이트 (ablation: 도움 안 되면 삭제, 발동률 상한)
```

근거:
- B 단독의 약점(미지의 언어)은 정확히 A의 강점과 겹침. 겹치는 곳에만 A를 쓰는 게 최소 비용.
- A 단독의 약점(비용·지연·비결정)은 B 기본값이 상쇄.
- 실측상 B가 이미 0.925/0.5초라, A는 나머지 0.075 + 실쿼리 롱테일을 노리는 포지션. 전체를 A로 뒤집을 이유가 수치상 없음.
- 역으로 B만 고집하면 top1 0.766 천장에서 규칙 accretion 지옥으로. A 폴백이 안전밸브.

## 5. 판단 기준 (언제 A를 켜나)

| 조건 | 의미 |
|---|---|
| deterministic 파서 슬롯 0개 | 코드가 이해 못 한 쿼리 |
| RRF top 점수 약함 (양쪽 리스트 불일치) | 텍스트도 못 찾음 |
| clarify 부적합 (물을 슬롯 없음) | 되묻기로도 안 풀림 |

셋 다 만족할 때만 LLM 1회 (쿼리 재작성, 출력 1문장, raw 병행). 그 외는 B. 발동률·적중률 별도 지표로 감시, 상한 초과 시 파서 개선으로 회귀.

## 6. 한 줄 결론

- **지금 당장 파워풀한 건 B** (측정済).
- **천장을 깨는 건 A의 조건부 투입** (미측정, 게이트付き).
- **절대 하면 안 되는 건 A 전면전환** (비용·지연·비결정성, 실측상 이득 증거 없음).
